# ADR 0001：核心用 C++20，构建用 CMake，core 不依赖 GUI

- 状态：已接受
- 日期：2026-11-16
- 决策者：架构组

## 背景

图像工作台要同时满足三件事：处理 4 亿像素大图时内存可控、批量处理吞吐够高、界面能长期演进。
候选方案有三条：全 Python、C++ 内核 + Qt 界面、Web 前端 + 服务端。

全 Python 的问题在内存与启动：一次卷积产生多层临时数组，大图上不可控；打包分发还要带解释器。
Web 前端的问题在色彩管理与大图渲染：浏览器内的 ICC 与像素级对比不可控，GPU 路径是黑箱。

## 决策

1. 核心与界面统一用 **C++20**，构建用 **CMake ≥ 3.24**。
2. `ft_core` **不依赖 Qt、不依赖 OpenCV**，只依赖 STL。几何与色彩原语自己实现，保证可测试、可移植。
3. GUI（v0.2）用 Qt 6，作为独立 target 链接 `ft_core` / `ft_ops`，**依赖方向只能向下**。
4. 训练用 Python，独立进程，产物是 ONNX；C++ 侧只加载 ONNX 推理（见 DESIGN.md §12.5）。

## 后果

**收益**

- 内存与延迟可控，大图分块与瓦片缓存有实现空间。
- 核心库可被 Qt 界面、CLI、插件、Python 扩展（后续 pybind11）复用，不存在「第二套实现」。
- 单文件部署，无运行时依赖（除系统 zlib）。

**代价**

- 开发速度慢于 Python；算子数量增长需要更多人力。
- 训练生态不在 C++，必须严守「Python 只做离线模型生产」的边界，否则会退化成双语言纠缠。
- Qt 引入后包体增大（详见 DESIGN.md §12.13），需要裁剪模块。

## 备选方案

- **全 Python + Qt(PySide)**：开发快，但 GIL 与内存峰值不可接受，且分发体积更大。
- **Rust 核心**：内存安全更好，但图像与 CV 生态弱于 C++，团队学习成本高。
- **Web 前端 + WASM**：跨平台好，但大图与色彩管理无法达标。

## 复核条件

若出现以下情况，重新评估：

1. `ft_core` 的算子实现被验证为性能瓶颈，且 GPU 路径收益超过 5×；
2. 团队规模小于 3 人，C++ 迭代速度成为主要约束；
3. Qt 许可或包体成为分发阻碍。
