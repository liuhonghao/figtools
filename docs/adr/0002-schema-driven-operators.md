# ADR 0002：算子由 schema 描述，参数规范化负责复现性

- 状态：已接受
- 日期：2026-11-16
- 决策者：架构组

## 背景

图像处理工具的可信度取决于**同一配方跑出同一结果**。但参数在实现里天然是松散的：

- 有的算子吃 `double`，有的吃枚举字符串，有的吃百分比；
- 参数名在代码、配置文件、界面三处各写一遍，改名就会漂移；
- 缺省值散落在实现里，`if (!has("radius")) radius = 1;` 这种代码无法被界面发现；
- 参数越界没有统一处理，有的截断、有的报错、有的算出诡异结果。

结果是：配方能跑，但换台机器、换个版本，结果就变了，而且没人说得清为什么。

## 决策

1. **参数只存在于 `OperatorSpec`**，实现通过 `Params::number/integer/boolean/text` 取值，
   不得自行解释缺省值。
2. **`Registry::normalize()` 是唯一入口**：填充缺省值、校验类型、校验范围、拒绝未声明参数，
   返回一个「键集合恰好等于 schema」的规范化参数集。
3. **规范化结果是缓存键的输入**。`cache_key = H(input, seed, recipe.version, Σ H(op, op.version, params))`。
4. **改变输出行为必须升 `OperatorSpec::version`**，否则旧缓存会命中新结果。
5. 未声明参数**报错而不是忽略**。静默忽略会让「参数名写错」这种低级错误潜伏到线上。

## 后果

**收益**

- CLI 帮助、GUI 控件、参数校验、缓存键四处共用一份定义，不存在漂移。
- 参数错误在「开始前」暴露（`validate_recipe`），而不是跑到第 3000 张图才崩。
- 配方可 diff：规范化后键序固定、数值格式固定（`%.10g`），同一配方两次导出字节一致。
- 新增算子只需写一个 `.cpp` + 一段 schema，不改任何框架代码。

**代价**

- 每个算子要多写约 20 行 schema，比「直接读 parm」啰嗦。
- 枚举参数在 schema 里以索引存默认值，序列化时需要转回字符串，实现上有一个小拐弯。
- 浮点参数的哈希用 `memcpy` 取位模式，意味着 `1.0` 与 `1.0000000001` 是两个不同的键——
  这是刻意的：宁可多跑一次，也不要「看起来一样但结果不同」。

## 备选方案

- **无类型参数表（`map<string,string>`）**：实现简单，但校验、界面、文档全部要重复解析。
- **Protobuf 定义参数**：跨语言好，但引入编译期代码生成，v0.1 阶段过重；后续做插件 ABI 时可考虑。
- **只靠单元测试保证复现**：测试发现不了「参数名写错被忽略」，因为缺省值让结果看起来正常。

## 复核条件

若算子数量超过 200，schema 的声明成本成为主要负担时，考虑用代码生成（从 YAML 生成 schema 与文档）。
